פתחו הגדרות → קופה ואת הפרופיל המתאים. הגדרות שירות מלא הישנות מפנות לפרופיל ברירת המחדל.

<span id="menu-behavior" />

## הגדרת התנהגות תפריט

פתחו התנהגות תפריט ובחרו הגדרות בחירה, תוספות וניווט. שייכו פרופיל למכשיר ובדקו פריט עם בחירת חובה כדי שלא ידלגו עליה. פרופיל מצב קופה אינו משייך מדפסת מטבח. הגדירו בנפרד את פרופיל ההדפסה המשותף להתקנת קופה זו; ראו [שיוכי מדפסות ומסמכים ממתינים](/he/help/printers/profiles-and-routing#assign).

<span id="courses" />

## הגדרת שלבי הגשה

פתחו שלבי הגשה והגדירו שמות וסדר. בדקו השהיה ושיגור בפרופיל הקופה. שלבים מארגנים שיגור למטבח ונפרדים מפיצול חשבון ומקבוצות תפריט.

<span id="adjustments" />

## בדיקת התאמות מותרות

פתחו התאמות ובדקו סיבות והתנהגות להנחות, על חשבון הבית וביטול. נדרשות הרשאות מתאימות. ספריית הנחות קופה וקודי מבצע מקוונים מנוהלים בנפרד.

<span id="forgotten-device-assignment" />

## שמירת הגדרות לאחר שכחת מכשיר או החלפתו

שיוך ישן של מצב קופה למכשיר שכבר נשכח במסעדה זו לא אמור לחסום שמירה של הגדרה אחרת, למשל מועד הבקשה לבחור שיטת ביצוע. טיפול זה דורש גרסת API הכוללת ניקוי שיוכים למכשירים שנשכחו; הוא אינו מובטח בהתקנות ישנות. השמירה מסירה רק את השיוך הישן לאותו מכשיר שנשכח. היא אינה מפעילה אותו מחדש ואינה משייכת אוטומטית את מחליפו. לאחר רישום מכשיר חלופי, פתחו בניהול את מצב הקופה הרצוי, בחרו **מכשירים משויכים**, סמנו את המכשיר הנוכחי ואז **החל** ו**שמור**. בדקו את השיוך שנשמר; פרופילי ההדפסה נשארים נפרדים. אם השמירה עדיין נכשלת, שמרו את הטיוטה ואת הודעת השגיאה ובדקו את גרסת ה־API המותקנת לפני ניסיון נוסף. אין למחוק מצבים אחרים או לחזור על הפעלות כדי לעקוף את השגיאה. שיוך חדש למכשיר חסר, נשכח או השייך למסעדה אחרת עדיין נדחה.

<span id="terminal-batch-separation" />

## הפרדה בין הפקדות מסוף להתנהגות הקופה

פעולות אצוות המסוף אינן משנות את פרופיל השירות בקופה, משמרת הצוות או מגירת המזומנים. מנהל עם payments.manage פותח עוד ← דוחות ← הפקדות המסוף ב-Victa Portable מוגדר או ב-iPad/Victa Mini. פעלו לפי מדריך התשלום בקופה לאישור סוף היום ולטיפול בתוצאה לא ודאית; הגדרות תפריט או התאמות אינן מסדירות אצווה.

<span id="fulfillment-methods" />

## הגדרת אפשרויות המסירה בקופה

עם הרשאה לעריכת הגדרות, פתחו הגדרות → שיטות ביצוע → קופה ואז **ניהול לפי סניף**. בדקו את שם המסעדה בחלון שבמרכז המסך: הבחירות משותפות לקופות המסעדה ולא מוגדרות בנפרד לכל פרופיל מכשיר. אם השרת אינו תומך בשיטות מותאמות, הודעה מסבירה מדוע העריכה אינה זמינה. הוסיפו או ערכו שיטה, תנו לה שם תצוגה ייחודי ובחרו סוג הזמנה: ישיבה במקום, איסוף או משלוח. **סיום** מעדכן רק את הטיוטה; סגירת עורך השיטה מבטלת את העריכה שלא אושרה. השאירו לפחות שיטה פעילה אחת ולא יותר מעשר שיטות. שנו סדר בחצים או בידית הגרירה; השיטה הפעילה הראשונה היא ברירת המחדל. שיטה שהושבתה אינה מוצעת לבחירות חדשות. לחצו **שמירה** בניהול לפי סניף כדי לשמור את כל ההגדרות. סגירה עם שינויים מבקשת לאשר את ביטולם. אם השמירה נכשלת או שהשרת אינו מאשר את כל השדות שנשלחו, שמרו את הטיוטה, בדקו את השגיאה ואמתו את ההגדרות השמורות לפני שמניחים שהשינוי הוחל. הזמנות קיימות שומרות את השיטה שנרשמה; שינוי שם או השבתה אינם משנים את ההיסטוריה שלהן.

<span id="fulfillment-prompt" />

## בחירת מועד הבקשה מהצוות

באותו חלון הפעילו את בקשת הבחירה מהצוות ובחרו **בתחילת כל הזמנה חדשה** או **אחרי לחיצה על תשלום או שליחה**. כיבוי והפעלה מחדש של הבקשה במהלך העריכה משחזרים את המועד שבחרתם; שמרו במפורש. כשהבקשה כבויה, ברירת המחדל חלה על מכירה חדשה שלא שויכה. שולחן או חשבון בשם שכבר קיימים שומרים על סוג ההזמנה ועל מחזור השירות שלהם. בקופה, בחירת שורה בחלון רק מכינה את הבחירה: **שמירה** מחילה אותה וסגירה או ביטול משאירים את המכירה ללא שינוי. אם הבקשה בתחילת ההזמנה בוטלה, יידרש אישור שוב לפני שליחה או תשלום. טופס פרטי הלקוח האופציונלי מוגדר בנפרד לכל שיטה; אין מתג מעקב נפרד לכל שיטה. כל ההזמנות השמורות נשארות זמינות ב**הזמנות → הכול** בקופה ובמנהל, לפי מסעדה, הרשאות ומסננים; מצב התשלום ומצב ההכנה נשארים נפרדים. כשהבקשה לבחירת שיטה כבויה, טיוטה ששוחזרה שומרת על השיטה שנבחרה במפורש במקום לחזור לברירת המחדל. אם השיטה הושבתה מאז, פתחו פעולות → אפשרויות מסירה ובחרו שיטה חדשה במפורש לפני ההמשך.

<span id="tableless-open-checks" />

## שימוש בחשבונות פתוחים למכירות במקום

אין מתג נפרד לישיבה במקום ללא שולחן. השאירו שיטת ישיבה במקום זמינה בקטלוג המסירה של המסעדה. במצב הקופה המשויך למכשיר פתחו **חשבונות פתוחים**, הפעילו **שימוש במצב זה** ושמרו לפי הצורך. שמות כרטיסים מוגדרים מראש נשארים אופציונליים. גרסאות API וקופה תואמות יציעו [חשבון חדש ללא שולחן](/he/help/orders/order-types#pos-tableless-dine-in). אם האפשרות אינה זמינה בדקו את הודעת התאימות ואת מצב המכשיר בפועל; אין צורך להפעיל הגדרות מושבים או משלוח שאינן קשורות. לא נוצר שולחן מלאכותי וכללי הזמנות אונליין ו־QR אינם משתנים. ההזמנות שנוצרו לישיבה במקום מוצגות בהזמנות במנהל גם ללא שולחן; טופס ההזמנה הידנית במנהל נשאר מיועד לאיסוף ולמשלוח בלבד.

<span id="fulfillment-customer" />

## בקשת פרטי לקוח לפי שיטה

נדרשות גרסאות API וקופה תואמות. בעורך השיטה הפעילו **הצגת מסך פרטי לקוח**, בחרו **סיום** ושמרו את הגדרות המסעדה. בקופה, בחירה זו לכל החשבון פותחת טופס שם וטלפון אופציונלי, גם לברירת המחדל כשבקשת הבחירה כבויה. שמירה מאשרת יחד שיטה ופרטים; ביטול משאיר את המכירה ללא שינוי והטופס יתבקש שוב לפני שליחה או תשלום. בחירת פריט אינה פותחת אותו. שם: עד 80 תווים. טלפון שאינו ריק: עד 32 תווים בסך הכול, ובהם 7–15 ספרות, + אופציונלי בתחילתו ומפרידים רגילים. לא נוצרים חשבון לקוח, כתובת או הסכמה לשיווק. הודעות שהוגדרו עשויות להשתמש בטלפון: בדקו את ההגדרות לפני הזנת פרטים אמיתיים. לשונית לקוח מציגה פרטים שמורים. משלוחי מנות נוספים למטבח יורשים פרטים עקביים בלי אישור יצירה נוסף לכל שלב; הודעות סטטוס נשארות נפרדות. חשבונות מרובי לקוחות או מפוצלים אינם יכולים לאמץ לקוח חלופי. אם ה־API אינו תומך או שההקשר משתנה, פתחו מחדש את התהליך; טיוטת המקור נשמרת ויעד תפוס אינו נדרס.
